## 3. 播放：首轮「不可判定」，第二轮换源后**通过**

播放器确实进入了 `VideoActivity` 并显示了完整浮层（标题、时长、码率、简介、按钮），
但**播放没有真正推进**：

```
10-14 15:09:12.055  15046  D VideoActivity: onTimeChanged: isOwner=true mHistory=true
10-14 15:09:12.057  15046  D VideoActivity: onTimeChanged:
        position=-9223372036854775807 duration=2629568 canSave=false
```

- `position = -9223372036854775807`（`Long.MIN_VALUE`）= **位置未知哨兵值**，每秒重复，从未变化；
- `duration = 2629568` ms = 43:50，与界面上的 `00:00 / 43:50` 一致；
- 界面速率恒为 **`0 KB/s`**（同一帧在 15:06:56 曾读到 `26.1 MB/s`，随后归零）。

即：播放器拿到了时长，但**没有拿到可播放的流**，进度始终停在起点。
对照 `MATRIX-D-T-20261014.md` §1 —— 那一行的音频播放有真实推进
（`PlaybackState {state=3, position=53919}`），所以不是"本行观测方法不对"，而是**这个源/这部剧在本机没有起播**。

**因此「播放无回归」既不能判通过，也不能判失败——记为不可判定。**
**（第二轮已撤回该结论：换源后播放正常，见 §3.5。）**

### 3.3 换第二部片复测（同为不可判定）

按 §7 的判据换了一部**电影**（`爆烈房客` / `Tenement.2026.1080p.VMX.WEB-DL.H.264.AAC.mkv`，

| 项 | 结果 |

但仍**不能**据此判定播放器回归——该源是"盘"类站点，其直链是否可用不受本仓库控制。

### 3.4 一个必须记录的方法论陷阱

为判断"画面到底有没有在动"，取相隔 6 秒的两帧做逐像素差，得到 **75.9% 像素变化**，
看起来像"视频在播"。但**这个结论是错的**：该详情浮层的背景是 **TMDB 背景图轮播**，
日志里可见 `TmdbHeaderView: 轮播切换到第 N 张`，轮播动画本身就会让全屏大幅变化。

**所以本行的播放判据只认 `onTimeChanged` 的 `position` 是否单调推进，不认帧差。**
（`MATRIX-D-T-20261014.md` 那行之所以可用，是因为它的音频播放有真实推进的 `PlaybackState`。）

#### 4.3.1 更正：上一轮的「流内无文本轨」不成立

上一轮把字幕欠项归因为「该集未观察到文本轨」。**本轮对该 fixture 的实测否定了这一说法**：

| 项 | 实测值 |
|---|---|
| 容器 | `sample-embedded.mkv`，`Duration=60.0s`，`TimestampScale=1e6`（ns/tick） |
| 轨道 | 1=`V_MPEG4/ISO/AVC`，2=`A_PCM/INT/LIT`，**3=`S_TEXT/ASS`（`Language=chi`）** |
| 簇 | **只有 2 个**：`cluster0 @ 0ms`、`cluster1 @ 4885ms` |
| cue | **4 条，全部在 cluster0**；容器 `PTS=0ms`、`BlockDuration=60000ms`（覆盖整个 60s） |
| 样式 | `Style: Default,Aileron,42`；`PlayResX=960 PlayResY=540` |

4 条 cue 的原文（`ReadOrder / Layer / 文本`）：

```
0 / 3 : {\an7\pos(50,440)\p1\1c&H80FF80&\3c&HFFFFFF&\bord2}m 0 0 l 100 0 100 30 0 30   ← 绿色绘图
1 / 0 : {\an5\move(100,100,800,100,0,8000)\t(0,8000,\frz25\fscx150)\blur1}ASS move + transform
2 / 1 : {\an5\pos(480,250)\fnNoto Sans CJK SC\fs38}中文字体回退 · é · العربية
3 / 2 : {\an5\pos(480,350)\kf150}Ka{\kf150}ra{\kf150}o{\kf150}ke {\kf300}timing
```

因为 cue 覆盖整个文件，**任何播放时刻都应有字幕可渲染**。所以上一轮「切轨看不出差别」
不能用「没有文本轨」解释，真实原因见 §4.3.3。

#### 4.3.2 字幕渲染能力：**通过**（有设备证据）

两条互相独立的设备证据表明本 build 的 ASS 渲染路径**确实工作**，且**按 ASS 时间轴演进**：

**证据 1 —— 上一轮的参考帧 `D-M-66-sub-on-paused.png`（本轮重新解读）**

该帧视频自带 OSD 时码为 `00:00:02.867`，画面里 **4 条 cue 全部渲染**：
青色旋转的「ASS move + transform」、白色「中文字体回退 · é · العربية」、
黄色「Karaoke timing」、左侧绿色绘图块，均带 ASS 描边/阴影。

关键是**动画相位可校验**：`\t(0,8000,\frz25)` 在 `t=2.867s` 的预期旋转角为
`25 × 2867/8000 = 8.96°`，而该帧实测倾斜约 **9°** —— 与 libass 的定时动画精确吻合，
说明这不是“静态贴图恰好相似”，而是**按 ASS 时间轴实时渲染**。

#### 4.3.3 新发现：同会话 seek 后，长 ASS 事件不再重放

**这是本轮最重要的新事实，也解释了上一轮为何「开/关字幕两图无差异」。**

单会话 A/B，**seek 是唯一变量**，且两次取样的视频内容几乎相同
（`colorfulSamples` 40208 vs 40518，说明画面没有被黑帧/缓冲替换）：

| 取样 | 到达方式 | `position` | 视频区字幕带近白像素 | 字幕 |
|---|---|---|---|---|
| **A** | 自然播放，**全程未 seek** | `40610ms` | **1299** | ✅ 「Karaoke timing」可见 |
| **B** | **同一会话内 seek 一次** | `56996ms` | **0** | ❌ 消失 |

文件：`D-M-103-A-natural-40610ms-cues-visible.png` / `D-M-104-B-after-seek-56996ms-cues-gone.png`。

**归因**：4 条 cue 的容器 `PTS=0`、时长 `60000ms`，即“起点在落点之前、落点之后仍活跃”的
**长事件**；而 seek 落到 `cluster1`（`>4885ms`）后只读该簇，起点在 `cluster0` 的事件没有被重放。
这正是 `E4-LIBASS` §6.2 预先判定的那一项：

> 「流式 MKV …… 必须保证落点前开始、落点后仍活跃的长事件可以重放」
> 「阶段 2 必须证明容器索引/受控预读可找回这些事件，或将该输入明确留在兼容路径」

**性质判定：记为该行为缺口，但不判为回归。** 理由有两条：

1. `E4-LIBASS` 设计文档本身已把该项列为**尚待证明的阶段 2 项**，属已知/待办范围，
   不是本行改动引入的退化；
2. 本行没有基线证据表明该行为在更早版本可用（无「曾经可用」的对照）。

**这条同时更正了上一轮的对照结论**：上一轮的 ON/OFF 对照是在
`seek 到 37912ms` 之后拍的，那时 cue 已因上述机制丢失，
所以「开/关字幕两图只差状态栏时钟」**不能**推出「切轨无效」，
它只说明**对照点选错了**。

#### 4.3.4 仍欠的证据

「播放中切换字幕轨」的同帧 ON/OFF/ON 往返**仍未完整取到**，因此不判通过、也不判失败：

- 要拿到有区分度的往返证据，必须在**事件已被投递**的状态下就地冻结再切轨（即不能先 seek）；
- 但本模拟器在最后阶段反复回收本包进程（`Killing … remove task`、`failed to attach`，
  内存其实富余：`MemAvailable≈3.0GB`），导致「打开设置面板 → 点『字幕』→ 进『选择字幕』→
  选项 → 截图」这条长链路多次中断。
- **已确认可达的部分**：`选择字幕` 对话框确实能打开，且选项为
  `关闭字幕` / `中文，SSA`（层级树见 `D-M-55-trackdialog-hierarchy.xml`）。

> 实际截图里两个字幕选项的 `selected` 属性都是 `false`（该 UI 用**颜色**表达选中，
> 不用 `selected` 属性），所以**不能**靠层级树判断当前选中的是哪一项——
> 这也是后续复验要注意的坑。

> 注：另有一条**独立**的字幕能力证据：`settings` 里「字幕设置」页存在
> （`SettingSubtitleFragment`：自动匹配、首选语言、字幕源）。
> 另需记录一个环境事实：`shared_prefs` 中 `subtitle_auto_match=false`。

## 6. 局限

1. 首轮同源试了 **2 部**片都停在起点；第二轮换源（`热播[采]`）后正常。
   两轮合并的结论是**该源当次不可用**，不是播放器缺陷——但**未逐源复现**，
   故「源可用性」本身不在本行结论内。
2. **不要用帧差判断播放**：本播放器的详情浮层背景是 TMDB 轮播，会让全屏像素持续变化（§3.4）。
   本行判据始终是 `onTimeChanged` 的 `position` 单调性。
3. 字幕（§4.3）：本 fixture **确有** ASS 文本轨，渲染能力已取证（§4.3.2）；
   仍欠的是「播放中切换字幕轨」的同帧 ON/OFF/ON 往返（§4.3.4）。
4. **§4.3.3 的 seek 行为缺口只在单一 fixture 上观察到**，尚未在“多个较短 cue”的真实字幕流上复现，
   也未与 `E4-LIBASS` 的实现逐行比对；本行只记录现象与 `E4-LIBASS` §6.2 的对应关系，
   不对“实现是否正确”下结论。
5. 字幕 UI 的选中态**不能用层级树 `selected` 属性判断**（两项都是 `false`，选中靠颜色表达）。
6. 设备是 1080×1920 的 LDPlayer 模拟器，不是真机；且第二轮期间设备经历了一次重启
   （`systemui` ANR），重启后本行未重复全部步骤。
7. 未做触控与 D-pad 双路径的可达性遍历。
8. 倍速只验证了 `1.0 → 1.5` 一档；0.5/2.0/5.0 等极值档未逐一验证。

## 8. 第三轮的设备与工具笔记（供后续复验复用）

这些是第三轮反复踩坑后固化的操作性结论，避免下次重走弯路：

1. **uiautomator 只在「暂停 + 控制层可见」时能拿到 idle**。
   播放中视频持续重绘 → `could not get idle state`；暂停但控制层已隐藏 → 同样失败。
   反过来可以把这个特性当**传感器**用：`dump` 成功 ⇒ 控制层可见；失败 ⇒ 已隐藏。
2. **`screencap` 不需要 uiautomator**。所以“零交互取样”可行：只用
   `input keyevent 127/126` 暂停/恢复，全程不点屏幕，控制层就不会被唤出，
   也就不会用它的白色文字污染字幕像素统计。
3. **暂停只认 `keyevent 127`（MEDIA_PAUSE）**：幂等，连发不反转。
   点控制层中心的 `play` 按钮会**同时**切换播放态与进度条，
   会产生「已暂停但 position 仍在跑」的假象。
4. **`state` 实测映射**：`1`=播放、`3`=暂停（position 冻结）、`4`=ENDED、`2`=缓冲/就绪过渡。
5. **播放历史会持久化**：同名文件续播到片尾（实测 `60010/60015/60022ms`），
   因此同名文件永远读不到 `cluster0`。**复制成新文件名**即可从 0 开始。
6. **自定义包的界面有时被 uiautomator 报成 `package="com.fongmi.android.tv"`**
   （本机同时装着上游包，且两者 `versionName` 都是 `5.6.0`、类名相同）。
   证据归属要靠**前台 Activity** 或 dump 内的资源 id 前缀 `com.silent.android.webhtv:id/` 判断。
7. **进度条拖拽的落点映射非线性**：同一 `timeBar`（`[178,597]-[794,675]`，`cy=636`）
   终点 `x=200→11955ms`、`210→3786ms`、`183→4775ms`、`195→4756ms`。
   不要猜公式，用“候选序列 + 实测 position 复验”的方式定位。
8. **本模拟器（`192.168.50.3:5561`）会间歇性回收本包进程**
   （`Killing … (adj -10000): remove task`、`failed to attach`），
   内存并不紧张（`MemAvailable≈3.0GB`、181 进程）。属瞬时抖动，重试即可，不是 OOM。
9. 本轮产出的取证脚本（均在 `.design-evidence/matrix/`，非生产代码）：
   `_dm-trip3.sh`、`_dm-scan.sh`、`_dm-calibrate.sh`、`_dm-experiment.sh`、`_dm-timeline.sh`、
   `_dm-dense.sh`、`_dm-clean.sh`、`_dm-driver.sh`、`_dm-decisive.sh`、`_dm-ask.sh`、
   `_dm-trio.sh`、`_dm-toggle2.sh`、`_dm-seek-ab.sh`；
   以及 fixture 解析脚本与输出 `fixture-ass-parse.txt`。
