# 手机版全屏比例选择弹窗高度适配设计

## 背景

手机版横屏全屏播放时，从底部控制栏打开“缩放比例”弹窗，部分设备会把列表末尾压到弹窗底部操作区之后。用户即使继续上滑，也可能无法完整看到或点击“自适应”和“自定义”。

在 `emulator-5554`（1920 x 1080、540 dpi）上已复现首屏底部选项被裁切。代码排查确认，共用的 `ChoiceDialog` 只在 Leanback 模式下调用 `adaptListHeight`；手机版依赖系统对 `WRAP_CONTENT` 窗口的被动压缩，列表的可滚动高度因此没有按实际可用空间重新计算。

## 目标

- 横屏全屏下，选择弹窗始终位于可见窗口内。
- 所有比例选项均可通过滚动完整显示并点击。
- 保持现有选项顺序、按钮尺寸、颜色、取消操作和选择回调不变。
- 不影响电视端方向键焦点逻辑，也不为比例弹窗复制一套专用实现。

## 方案

继续使用共享的 `ChoiceDialog`，在窗口完成首次布局后，对手机端和电视端都执行 `adaptListHeight(window)`。该方法通过 `getWindowVisibleDisplayFrame` 获取布局后的可见窗口边界，并直接测量滚动列表同级的标题、操作区、内边距和外边距。首次调整滚动高度并重新布局窗口后，再排队一次同样的测量，等待 `WRAP_CONTENT` 窗口的固定区域高度稳定；只有内容高度连同 32dp 安全边距确实超出可见边界时，才按“可见窗口高度 - 固定区域高度 - 32dp 安全边距”限制滚动区域。这样既不依赖横竖屏切换期间可能滞后的资源尺寸，也不会把首轮不稳定的弹窗高度误当成最终可用空间。

Leanback 专用的 `focusSelectedItem()` 仍保留在 `Util.isLeanback()` 条件内。这样高度约束属于所有终端的通用布局行为，而遥控器焦点仍只属于电视端交互。

不修改 `VideoAspectModeDialog` 的业务接口和 `VideoAspectRatioDialog` 的自定义比例输入流程。所有使用 `ChoiceDialog` 的选择列表同时获得同样的窗口高度保护。

## 状态与错误处理

高度调整在窗口布局完成后的 `post` 回调中执行，避免在视图尚未测量时读取空的可见边界。若弹窗、列表、滚动容器、其直接父容器或可见边界不存在，沿用提前返回逻辑，不抛出异常，也不改变取消或选择行为。纯计算函数会把负数输入收敛到零；内容能完整放下时返回期望高度，溢出时结果不超过扣除安全边距后的实际可用高度。

## 测试与验证

1. 新增聚焦的 `VideoAspectUiSourceTest`，要求 `adaptListHeight(window)` 在首次布局后的回调中、Leanback 条件之外执行，并要求首次改变列表高度后重新排队一次稳定测量；修改前测试必须按预期失败。
2. 为高度计算补充安全边距、可用空间不足、单项/两项短列表保持原高和无需收缩等边界测试，再运行定向测试及相关单元测试。
3. 构建并安装手机版 APK 到 `emulator-5554`。
4. 进入横屏全屏播放，打开“缩放比例”，验证弹窗完整位于屏幕内。
5. 滚动到末尾，确认“自适应”和“自定义”完整可见、可点击，取消按钮不遮挡列表。
6. 检查日志中没有新增崩溃、窗口或布局异常。

## 非目标

- 不调整比例模式定义、持久化或播放内核应用逻辑。
- 不重做弹窗视觉样式。
- 不修改底部播放控制栏的排列方式。
