### 3.5 第二轮：详情页已补齐（首轮「不可判定」撤回）

#### 3.5.1 首轮推断为什么错

首轮 §3 的结论建立在**静态推断**上：

```
VideoActivity.java:761-765  →  TmdbDetailActivity 只在 shouldOpenLegacyTmdbDetail(...) 成立时打开
shouldOpenLegacyTmdbDetail   →  canOpenLegacyTmdbDetail(key, id) && isTmdbDetailModeConfigured() && isStandaloneTmdbDetailMode(mode)
```

当时用的是 `buye-0` 源，据此认定「不是 TMDB 类型源 → 打不开详情页」。
第二轮读码发现该链路有**四个**条件，且当时设备上的取值全部满足：

| 条件 | 代码位置 | 设备实际值 | 满足 |
|---|---|---|---|
| `canOpenLegacyTmdbDetail` | `leanback/VideoActivity.java:649-653` | 非 PUSH、非音频站、非短剧、`TmdbSitePolicy.isEnabled` | ✓ |
| `isTmdbDetailModeConfigured` | `Setting.java:1174-1176` | `isTmdbMode(1)` ✓ 且 `getTmdbModel()==0` ✓ | ✓ |
| `isStandaloneTmdbDetailMode` | `Setting.java:1221-1223` | `mode` 为 `FUSION(0)` / `ENHANCED(1)` / `PLAYER(4)` 之一；实测 `detail_open_mode=1` | ✓ |
| `TmdbSitePolicy.isEnabled` | `TmdbConfig.isSiteEnabled` | 见 §3.5.2 | ✓ |

关键点：`getTmdbModel()` 的 `clampTmdbModel`（`Setting.java:1066-1068`）**只返回 `TMDB_MODEL_NATIVE`**，
所以 `isTmdbDetailModeConfigured` 实际退化为「`detail_open_mode` 是 TMDB 模式」。

而 `TmdbConfig.isSiteEnabled`（`bean/TmdbConfig.java:360-368`）在
`enabledSites` 为空、`allowedSites` 为空、`disabledSites` 只含 `[音][听][书][漫][短]` 时：

```java
if (matchesExact(disabledSites, key) || matchesExact(disabledSites, name)) return false;
if (matchesExact(allowedSites, ...)) return true;
if (matchesExact(sites, ...)) return true;                       // sites 为空 → 不命中
if (matches(disabledSites, key) || matches(disabledSites, name)) return false;   // 见下
return sites.isEmpty() || ...;                                   // → true
```

`matches()` 对 `[音]` 这类**方括号通配**只匹配「以该标记结尾」的站点名。
`热播[采]` 以 `[采]` 结尾、不以 `[音]` 结尾 → **不被排除** → 返回 `true`。
**即首轮所用的同一类「采集站」其实是允许 TMDB 详情的。** 首轮真正的失败原因是**没走到那条入口**
（首页「最近观看」首卡当时直接进了播放器），而不是源不受支持。

## 4. 回归核查（针对 `fad60a9b1e6` 的 C-T 修复）

C-T 修复改了 TV 卡片行间距与 `adapter_episode_card.xml` 的 `layout_marginEnd`（12dp → 20dp）。
后者是**播放器选集**用的布局，需要确认没有引入双重间距：

- `VideoActivity.java:3908` 的 `SpaceItemDecoration(spanCount, 12)` 加在
  **`updateUpstreamNativeEpisodeGridViewport()`** 里，即**原生列表模式**的选集网格；
- `adapter_episode_card.xml` 只在 **TMDB 卡片模式**使用
  （`mEpisodeGridAdapter.setUseTmdbCard(useTmdbCards)`，`VideoActivity.java:3604`）；
- 两种模式互斥（切换时会 `clearEpisodeGridDecoration()`，`VideoActivity.java:2538`）。

**结论：不存在 12+20 的双重叠加。** 卡片模式下的横向间距现在正好是 20dp（token 值）。
未在设备上触发 TMDB 卡片模式（见 §5.2），这一点是静态判定的。

播放器 OSD 本身未被本次改动触及；`D-T-01..08` 的渲染与焦点行为均正常。

### 4.1 D-pad 遍历：底栏可达但呈「环状」退化（评分类缺陷）

右推遍历底栏五个按钮（`D-T-35-bottom-1..5`）：

| 帧 | 焦点控件 | 文本 | 实测 bounds |
|---|---|---|---|
| 1 | `id/following` | 加入追更 | `[786,964][1132,1048]` |
| 2 | `id/rematch` | TMDB | `[1148,24][1494,108]` |
| 3 | `id/themeModeDetail` | 深色 | `[1510,24][1856,108]` |
| 4 | `id/themeModeDetail` | 深色 | 同上（帧与第 3 帧 sha 完全相同） |
| 5 | `id/themeModeDetail` | 深色 | 同上 |

问题：焦点从底栏（y≈964）跳到 **顶部**（y=24）的同一个按钮上，并**卡死**——
第 4、5 次右推产生**逐字节相同**的帧（`sha=95C145D2134119BE`），即焦点不再移动；
同时底栏对应的 `themeModeDetail` 按钮本身还在 `y=964`。
同一 id 在 `y=24` 与 `y=964` 各有一份，说明存在**两份布局**（顶部一份、底部一份）
同时挂在窗口里，D-pad 在两份之间绕圈而不再前进。

**判定：底栏五个按钮可被 D-pad 到达（可达性本身满足 §20.3 第 4 条前半），
但「焦点不会落入不可见区域 / 遍历应当收敛」这一条不满足 —— 记为不通过。**
这是本轮新发现的评分类缺陷，本任务为验收任务，**未修改生产代码**。

### 4.3 新缺陷：详情页进入播放后底栏被 16:9 全屏画幅裁掉

| 截图 | 焦点 | 底栏 y 区间 | 可见高度（0..1080） |

## 6. 局限

1. 首轮覆盖的是**音频播放器** OSD；第二轮补了真实视频流 OSD（§4.2）与详情页（§3.5）。
   视频专属项（字幕、清晰度、音轨）未在本行取证——属 D-M 的场景。
2. **TMDB 卡片模式仍未在设备上触发**，§4 的「无双重间距」仍是静态判定。
   本轮的详情页是 `TmdbDetailActivity`（§3.5），与其自带的选集卡片模式不是同一处判定点。
3. D-pad 遍历只做了**底栏 5 个按钮**的右推（§4.1）与播放 OSD 的 4 次右推（§4.2），
   未做全屏全量遍历。
4. §4.3 的位移是「同一按钮在不同焦点态下 bounds 变化」的实测，未取布局源码定位到具体规则。
5. 设备是模拟器（1080×1920 竖屏物理尺寸，leanback 强制横屏 → screencap 1920×1080；

### 7.3 环境坑（固化，供后续设备验收参照）

该 LDPlayer 实例（`ro.serialno=00aece4c`）的 `pm` 会**长时间无响应**，本轮遇到三次：

| 命令 | 表现 | 实际结果 |
|---|---|---|
| `adb install -r -d <apk>` | 300s / 600s 超时无输出 | **安装已完成** |
| `adb shell pm install -r -d <path>` | 600s 无输出 | **安装已完成**（`lastUpdateTime` 已更新） |
| `adb shell pm install-commit <id>` | 900s 超时 | 空转，无 `/data/app/vmdl*` 残留 |

**判据必须取包管理器状态，而不是命令是否返回：**

```bash
adb -s <dev> shell "dumpsys package com.silent.android.webhtv | grep lastUpdateTime"
adb -s <dev> shell "md5sum /data/app/<hash>/base.apk"   # 与本地 APK md5 比对
```

卡住时的稳定解法：`adb reboot` → 重新 `adb connect`（出栈时需 `adb start-server`），
再用 `pm install-create -S <size>` → `pm install-write -S <size> <id> base <device-local-path>`
→ `pm install-commit <id>` **分步**执行（本轮分步后 write 0.9s、commit 正常返回 `Success`）。
另：把 APK 先 `adb push` 到 `/data/local/tmp` 再安装（避免 `install-write` 从主机流式传输）明显更稳。

> Git Bash 下 `adb push <host> /data/local/tmp/...` 会被 MSYS 路径转换改写为 `G:/Git/data/...`，
> 需 `MSYS2_ARG_CONV_EXCL='*'`。
