## 1. 环境与模式

| 项 | 值 | 证据 |
|---|---|---|
| 设备 | `127.0.0.1:5559`（LDPlayer） | `adb devices` |
| 系统 | **Android 9 / API 28** | `getprop ro.build.version.sdk` = 28 |
| flavor | **mobile**（本次新装 debug 包） | 顶部工具栏 + 分类 chips + **底部四项导航**；`run-as` 可用 |

| **应用实际渲染调色板** | **深色表** | 实测 `#44474A` = `values-night` 的 `webhtv_color_secondary_container` |

### 1.1 模式判据的重要修正（影响此前所有行）

**`dumpsys activity top` 的 `mCurrentConfig` 只在 `theme_mode` 为「跟随系统」时才是模式判据。**

- `theme_mode = -1`（跟随系统）：AppCompat 的结果与系统一致，`mCurrentConfig` 会出现裸 token `night`。
  此前 B-M-D / B-M-L / B-T-D / C-T / D-T 各行的设备 `theme_mode` 都是 `-1`，因此那些行的 `mCurrentConfig` 判据**成立**。
- `theme_mode = 1`（显式深色，本行）：`AppCompatDelegate` 覆写的是 **Activity 的 Resources**，
  系统 `Configuration` 仍是浅色，所以 `mCurrentConfig` **不含** `night`，而应用实际渲染深色表。

本行因此改用**渲染出的 token** 作为判据（实测 `#44474A`，见 §1 表）。

## 2. 不依赖系统动态色

### 2.1 代码层：全仓库没有任何动态色调用

```
grep -rn "DynamicColors|applyToActivitiesIfAvailable|dynamicColor" app/src/main/java
→ 0 命中
```

即应用**不使用** Material You 的 `DynamicColors`（那才是"系统动态色"），
而是由 `ThemeResolver` 从自己的 seed 推导调色板。

### 2.2 设备层：系统浅色下仍渲染深色表

`ui_night_mode = 1`（系统浅色）而应用实测使用 `values-night` 的 token（`#44474A`）。
应用既不跟随系统夜间位，也不取系统动态色。

## 3. 手动 seed 与壁纸 seed

### 3.1 采集方式

在 mobile debug 包上用 `run-as` 依次改写 `theme_color` 并重启应用，各取一帧：

| 文件 | `theme_color` | 含义 |
|---|---|---|
| `B-A9-03-seed-none.png` | `-1` | 不做着色（编译期冻结调色板） |
| `B-A9-02-seed-wallpaper.png` | `0` | **壁纸 seed** |
| `B-A9-01-seed-explicit.png` | `-13730510`（= `0xFF2E7D32`，绿） | **手动 seed** |

采集后已把 `theme_color` 还原为 `-1`。

### 3.2 逐像素差异（对 `-1` 基线）

`-1` → `0xFF2E7D32`（手动 seed）：**27410 px 不同（1.32%）**

| 基线色 | 变为 | 像素数 | 归属 token（深色表） |
|---|---|---|---|
| `#44474A` | `#3B4B38` | 8485 | `webhtv_color_secondary_container` → **偏向 seed 的绿** |
| `#C4C6D0` | `#C2C9BD` | 1832 | `webhtv_color_on_surface_variant` → 偏绿 |
| `#E2E2E6` | `#D6E8CE` | 535 | `webhtv_color_on_secondary_container` → 偏绿 |

`-1` → `0`（壁纸 seed）：**23338 px 不同（1.13%）**

| 基线色 | 变为 | 像素数 | 判定 |
|---|---|---|---|
| `#44474A` | `#494458` | 8485 | → **偏向壁纸的紫** |
| `#C4C6D0` | `#CAC4CF` | 1832 | 偏紫 |
| `#E2E2E6` | `#E7DFF8` | 535 | 偏紫 |

**结论**：三种取值产生三套可区分且方向正确的调色板——
无 seed 用冻结表、壁纸 seed 取壁纸色相、手动 seed 取指定色相。
被改写的都是"承载强调色"的角色（`secondary_container` 及其 on 对），符合设计意图；
差异占比小（1.1–1.3%）是因为 `ThemeBinder` 只改写受控角色，不整屏重绘。

## 4. resolver 日志与 fallback

"resolver 日志"在本仓库是 `ThemeResolver.lastDiagnostic()`（`ThemeResolver.java:336`），
由测试直接断言：

```
./gradlew :app:testMobileArm64_v8aDebugUnitTest --tests 'com.fongmi.android.tv.theme.*'
→ BUILD SUCCESSFUL in 2m 55s
```

`ThemeResolverTest` 覆盖本行的两个要点：

| 测试 | 断言 | 对应本行标准 |
|---|---|---|
| `noSeedUsesTheFrozenPalettes` | 无 seed 返回 `ThemeTokens.light()/dark()` | 无 seed 基线 |
| `explicitSeedGeneratesAContrastingPaletteInsteadOfReturningTheSeed` | 手动 seed 生成对比度达标的调色板而非直接返回 seed；诊断 `seed:explicit` | **手动 seed** |
| `wallpaperSeedRemainsADarkSurfaceAndNeverBecomesText` | 壁纸 seed 不会变成 surface/文字；`requireContrast()` 通过 | **壁纸 seed** |
| `androidNineFallbackUsesTheDefaultPalette` | `ThemeMode.SYSTEM + ThemeSeed.NONE` → `ThemeTokens.dark()` | **Android 9 fallback** |
| `invalidSeedFallsBackWithoutThrowing` | 非法 seed 不抛异常并回落；诊断 `fallback:invalid-seed` | **fallback 正确** |
| `lowContrastCandidateFallsBack` | 低对比候选回落；诊断含 `seed-contrast` | **fallback 正确** |

`ThemeResolverOverrideTest` 另外断言 `default` / `profile` / `last-good` / `fallback` 四类诊断串。

## 6. 局限

1. 设备是 1920×1080 / 280dpi 的模拟器，不是真实 Android 9 手机；
   "Android 9" 的覆盖是 API 级别 + `androidNineFallbackUsesTheDefaultPalette` 的静态断言。
2. §3.2 的差异是**像素级对照**，未逐角色枚举调色板全部槽位；
   覆盖的是屏幕上实际出现强调色的角色。
3. 本行为取到 mobile flavor，在 5559 上安装了 `app-mobile-arm64_v8a-debug.apk`
   （覆盖该机原有的 leanback 构建）。这是设备状态变更，不是产品变更。
4. 5554 上装的是 **release 包**（`run-as: package not debuggable`），无法用同一手法改写偏好，
   因此未在 5554 上复验。
5. 未验证「壁纸变更后自动重新推导」的实时路径（只验证了显式设定 `wall_color`/`theme_color` 后的结果）。
